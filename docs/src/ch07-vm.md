# スタック VM

インタプリタはプログラムの意味を定める「仕様」でした。この章では、同じプログラムを実行する別の機械——**スタック VM**——を定義します。Java の JVM や Python の CPython と同じ、命令列をプログラムカウンタで順に実行する方式です。

## 命令

```lean
{{#include ../../Simplean/VM.lean:instr}}
```

| 命令 | 動作 |
|---|---|
| `push v` | 値 `v` をスタックに積む |
| `load x` | ローカル変数 `x` の値を積む |
| `store x` | スタックトップを取り出して `x` に格納 |
| `unop op` | トップを取り出し、演算結果を積む |
| `binop op` | 上 2 つを取り出し、演算結果を積む |
| `jmp ofs` | 相対ジャンプ |
| `jz ofs` | トップを取り出し、`0` なら相対ジャンプ |
| `call f` | 関数 `f` を呼ぶ |
| `ret` | 関数から戻る |
| `halt` | 停止 |

ジャンプは**相対**です。`jmp ofs` は「次の命令の番地に `ofs` を足した番地へ」飛びます。相対にしておくと、命令列を別の場所に置いても意味が変わりません。これが第 10 章の証明で「コード片 `c` が番地 `pc` から置かれている」という述語（`CodeAt`）を素直に使える理由です。

ローカル変数は、インタプリタと同じ連想リストで、**名前で**アクセスします。実際の VM は番号付きスロットを使いますが、名前のままにしておくと「VM のローカル変数＝インタプリタの環境」という等式がそのまま成り立ち、証明が簡単になります（CPython にも `LOAD_NAME` という名前ベースの命令があります）。

## 状態

```lean
{{#include ../../Simplean/VM.lean:vmstate}}
```

VM プログラムは命令列と**関数表**（関数名 → 入口番地と引数名）から成ります。状態は、プログラムカウンタ `pc`、オペランドスタック、ローカル変数、そして**呼び出しフレームの列**です。フレームは「戻り番地」と「呼び出し元のローカル変数」だけを保存します。オペランドスタックは保存しません——呼び出し元の残りのスタックの上で、そのまま呼び出し先が動くからです。

## 1 ステップ実行

```lean
{{#include ../../Simplean/VM.lean:step}}
```

`step` は現在の命令を取り出し、命令とスタックの形で場合分けします。結果は `Option VMState` で、`none` は「停止（`halt`）」または「不正な状態（スタックが足りない、型が合わない、番地が範囲外）」です。

`call f` の動きを追います。

1. 関数表から `f` の入口番地と引数名を取り出す
2. 引数の個数 `k` ぶん、スタックから値を取り出す。引数は左から順に積まれているので、`take k` して `reverse` すると元の順になる
3. 引数名と値を束ねて新しいローカル変数を作る（インタプリタと同じ `bindParams`）
4. 戻り番地 `pc + 1` と現在のローカル変数をフレームに保存し、入口番地へ飛ぶ

`ret` はその逆です。スタックトップに戻り値がある状態でフレームを取り出し、戻り番地とローカル変数を復元します。戻り値はスタックに残ったままなので、呼び出し元から見ると「`call` の前に積んだ引数が消えて、戻り値が 1 つ積まれた」ことになります。

演算の意味 `applyUn`/`applyBin` は、インタプリタと**同じ関数**です。VM 用に書き直していません。これはコンパイラ正当性の証明で大きく効きます——演算に関する部分は「同じ関数を呼んでいるから同じ」で済むのです。

## 実行

```lean
{{#include ../../Simplean/VM.lean:run}}
```

`run` は最大 `fuel` ステップ実行し、`halt` に到達したらスタックトップを返します。ここでも fuel を使います。VM の `step` は 1 ステップで必ず終わりますが、それを繰り返す `run` は停止しないかもしれないからです。

## 手でトレースする

小さな命令列を手で追ってみましょう。`1 + 2` をコンパイルすると（次章）、次の命令列になります。

```text
0: push (int 1)
1: push (int 2)
2: binop add
3: halt
```

| pc | 命令 | 実行後のスタック |
|---|---|---|
| 0 | `push (int 1)` | `[1]` |
| 1 | `push (int 2)` | `[2, 1]`（左がトップ） |
| 2 | `binop add` | `[3]` |
| 3 | `halt` | 停止、結果 `3` |

`binop` は「上 2 つを取り出す」ので、スタックトップ `2` が右オペランド、その下の `1` が左オペランドです。`step` の `| .binop op, v₂ :: v₁ :: σ => … applyBin op v₁ v₂` がその順序を決めています。引き算のような非可換な演算で順序を間違えると、コンパイラ正当性の証明が通りません。証明は、こういう「ありがちな実装ミス」を漏れなく捕まえてくれます。
